# 需求基线 v1

## 目标

构建一个 Pi 原生 Plan & Execute 插件：高能力 Planner 将简短需求转化为本地、分层且版本化的计划包；经用户批准后，低成本 Coder 按任务执行，并在需求变化时保留完整历史和可恢复进度。

## 用户故事与验收标准

### R1 — 低提示成本的规划入口

作为用户，我只需给出简短目标，系统便自动应用预设 Planner 角色和工作流。

- `/mgood:plan <自然语言需求>` 可创建计划，不要求用户粘贴规划模板。
- Planner 会自动探索仓库、记录假设，并只在阻塞性信息缺失时提问。
- 生成结果在保存前可预览；取消不得留下半写文件。

### R2 — Planner/Coder 模型分离

作为成本敏感的用户，我可以让不同能力/成本的模型承担规划和编码。

- Planner 和 Coder 使用两个独立、可配置的模型引用。
- 启动操作前展示实际 provider/model；解析失败时明确报错，不静默回退。
- Planner 默认只读；Coder 只在已批准执行阶段获得所需写工具。
- 每次模型调用均可取消，并记录模型身份和时间，不记录凭据。

### R3 — 可配置且可见的本地存储

作为个人或团队用户，我可以选择计划是否进入 Git。

- 支持 `collaborative`、`personal`、`custom` 三种模式。
- 默认建议 `docs/plans` 用于团队留档，`tmp/plans` 用于个人临时计划。
- 创建前报告目标路径及 Git tracked/ignored/untracked 状态。
- 插件不自动修改 `.gitignore`、不自动 stage/commit，custom 路径不能逃逸允许的根目录。

### R4 — 分层计划包

作为评审者，我可以分别阅读背景、需求、实施步骤和历史。

- 每个功能位于稳定的 `YYYY-MM-DD-description/` 目录。
- 至少生成 `README.md`、`CONTEXT.md`、`requirements/vN.md`、`implementation/<timestamp>-vN.md` 和 `HISTORY.md`。
- 实现计划包含稳定任务 ID、Markdown checkbox、依赖、影响路径、验证和完成标准。
- 所有机器读取 metadata 都有 schemaVersion/版本、状态和时间字段并通过 schema 校验。

### R5 — 审批后逐任务执行

作为用户，我可以在可控边界内执行、暂停和恢复计划。

- `/mgood:execute` 默认只选择一个依赖已满足的任务并展示预览。
- 开始写操作前需明确批准；非交互模式必须提供显式确认参数。
- 任务成功必须有验证证据；失败或中止不得错误地勾选完成。
- 恢复时从磁盘当前指针和任务状态继续，不依赖原聊天上下文。

### R6 — 部分执行后的需求变化

作为用户，我可以改变方向而不抹去已完成工作的由来。

- `/mgood:revise <变化>` 先生成影响分析，再决定原地修订草稿或创建新版本。
- 执行已开始且变化影响需求、方案、任务语义、依赖或验收标准时，必须创建新版本。
- 旧版本保留并标记 `superseded` 或 `abandoned`；不得删除。
- 新版本明确列出继承、替换、新增、删除的任务；已完成工作附证据 carry forward，默认不重复执行。

### R7 — 可审计历史

作为维护者，我可以理解计划为何变化、执行过什么以及由谁确认。

- `HISTORY.md` 追加记录创建、批准、执行、修订、替代、完成和放弃事件。
- 事件包含时间、版本、原因、主体（user/system/model）和相关任务；敏感信息必须脱敏。
- 当前版本指针采用原子更新；并发修改会被检测而不是最后写入者静默覆盖。

### R8 — Pi 生命周期和运行模式

作为 Pi 用户，我在 TUI 和非交互环境中都得到安全且可预测的行为。

- 交互命令提供取消、简短描述、模型/路径/变更摘要和有用错误。
- `print`、`json`、`rpc` 模式不调用不可用的 TUI API；需要交互时给出可操作错误。
- AgentSession、进程或其他资源只在 session start 后或懒加载创建，并在 shutdown 幂等清理。

### R9 — 工程质量和文档

- 领域逻辑可在无真实 TUI、模型或 Git remote 时测试。
- schema、路径安全、版本迁移、审批门、取消/恢复和插件注册生命周期有自动测试。
- 包 README 记录安装、权限、配置、数据位置、非交互行为、恢复和卸载。
- format、lint、typecheck、test、build/pack 检查通过。

## 非功能要求

- TypeScript ESM、strict、Node 22+、npm workspaces。
- 使用仓库统一的 TypeBox 方案验证配置、模型输出和磁盘内容。
- 运行时依赖放在 `dependencies`，尽量使用 `node:` 内置模块。
- 诊断结构化且脱敏；文件、模型、子会话操作支持 `AbortSignal`。
- 首版不联网同步计划，不隐式索引源码，不实现上下文管理。

## 待产品确认但不阻塞 v1 规划的默认值

1. `collaborative` 是否应成为全局默认？**建议：**首次使用让用户选一次，项目配置存在后不重复询问。
2. 是否允许连续自动执行多个任务？**建议：**v1 默认且上限均为 1，稳定后再增加“批准 N 个任务”。
3. Coder 是否必须创建 Git checkpoint？**建议：**v1 只记录起始 HEAD/dirty 状态，不自动 commit/stash；未来与 Git 插件集成。
